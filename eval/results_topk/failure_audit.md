## 2. 哪些类型的判定是硬的，哪些是软的

| 类型 | 判定依据 | 可靠性 |
|---|---|---|
| 未召回 | gold pid ∩ 检索集 = ∅ | **硬**（纯集合运算，不依赖文本判分） |
| 召回未读入 | gold 在检索集但不在上下文 | **硬**（同上） |
| 读入推理错 | gold 在上下文 且 f1 < 0.5 | 软：依赖 token-F1 对「同义/缩写/整句 gold」的容忍度 |
| 引用错配 | f1 ≥ 0.5 且 cit_p < 0.5 | 软：cit_p 只认标注 gold，会低估「引用正确但未标注」的情况 |

结论：**机制段结论（「召回未读入」从 153 条归零、该类失败 67.6% 转为成功）用的是前两类，属硬判定，不受上述争议影响。**
需要打折扣的是「读入推理错 / 引用错配」两类的**占比解读**，不是它们的**存在性**。

## 3. 两条按优先级取类的副作用

`failure_class` 是单标签、按顺序取第一个满足的条件，因此一条记录只暴露「最靠前的那个问题」：

- `未召回-1`：答案对、引用全错、gold 完全没检索到 → 记为「未召回」，但真实失败原因是引用。
- `召回未读入-4/-5`：gold 没进上下文，同时模型被相邻干扰段误导答错 → 记为「召回未读入」，
  而「多给槽位」确实能修好它（gold 一旦进上下文，干扰段就不会独占）。
- `引用错配-1`：答案错（26 vs 25）且引用散 → 记为「引用错配」，但主因是答案错。

这不影响「加槽位能救哪一类」的因果解释（那正是按「缺什么」排序的），但**不能反过来**用类别占比去说
「模型推理错误占 75%」——一条记录可能同时是推理错和引用错。

     不影响 Δ。
